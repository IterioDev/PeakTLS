### Notes on segment 3

A MISMATCH HERE IS ABOUT THIS RECORDING'S CALLER, NOT ABOUT THIS LIBRARY, and
reading it the other way is the mistake subsystem B's Finding 1 is entirely about.
The rows score the ClientHello these datagrams carried, and whoever built that
ClientHello chose its transport parameters. A connection built through
TlsQuicClientHelloProfileFactory emits TlsQuicTransportParameterSpec's shipped
preset and reproduces the capture's fourteen exactly, which is asserted by
TlsQuicFingerprintReadoutTests.TheShippedPresetReproducesTheCapturesSegmentThree.
A connection whose caller hand-composed a shorter list emits the shorter list,
and this table says so.

EVERY ROW IS SCORED AT ITS INDEX, NOT BY MEMBERSHIP. Capture line 74 says the
ordering is the fingerprint, and commit 4ed90bf measured it against the live
service 12/12: reordering the parameters moved perk_hash and left
perk_hash_normalized byte-identical. A set comparison would score a sorted list
as a match, and a sorted list is a different client.

THREE ROWS ARE SCORED ON POSITION BECAUSE THE SERVICE DOES NOT HASH THEIR VALUES.
The perk string renders 12583 and 15 as AUTO (capture lines 98-99) and the
reserved parameter as the bare token GREASE, so their tokens carry an identifier
and no number; commit 4ed90bf confirmed it from the other side, by sending
initial_rtt at 100000 and at 900000 and moving neither hash. Those rows therefore
say "an AUTO-rendered 12583 was emitted thirteenth" and claim nothing about the
microseconds inside it. The same measurement found the service strips neither an
unknown identifier nor a zero-length value, so an emitted 12583 or 15 is a token
the service really does render rather than one it might drop.

THE GREASE VERSION INSIDE version_information IS NOT IN THE THIRD COLUMN, and its
absence from it is a result rather than an oversight. RFC 9368 s3 bounds the form
exactly - "versions following the pattern 0x?a?a?a?a" - so row 9's GREASE token
is produced by recomputing that predicate over the four emitted bytes. A version
outside the pattern renders as its own number and the row fails. What the capture
leaves open is only WHICH member of a 16^4 set Chromium drew, and the perk string
tokenises that, so nothing about it is unknown here.

THE TWO ROWS THAT ARE IN IT ARE BOTH WIDTHS, AND BOTH ARE TASK B12's. The capture
publishes one initial_rtt draw and five significant digits of one reserved
identifier; neither bounds the interval it came from, and only a packet capture
can. Both rows still render the draw THIS connection made, so they measure
something even while their verdict says the target does not settle it.

## Known deviations from the target, named rather than omitted

1. initial_rtt'S RANGE IS UNVERIFIED - THE PARAMETER ITSELF IS SENT. This entry used
   to say that nothing sent Google-private parameter 12583 at all, and that was true
   when it was written. Tasks B5 and B8 made it false: the preset in
   TlsQuicTransportParameterSpec carries a DrawnInitialRtt entry that redraws a
   microsecond value per connection, and B8's TlsQuicClientHelloProfileFactory is what
   puts the composed blob into the ClientHello - so a connection built through that
   factory emits 12583. TlsQuicConnectionSpec.InitialRttRange is still null by default,
   but a null now OVERRIDES nothing rather than suppressing the parameter: the preset
   entry's own fallback range is what it falls back to.
   WHAT REMAINS UNSETTLED IS THE RANGE AND NOT THE PRESENCE. The Brave capture holds
   exactly one draw (value 192859), which fixes neither bounds nor distribution, so the
   preset's interval is marked unverified where it is declared. Bounding it - by
   capturing enough connections, or by reading uQUIC's ChromeRandomInitialRTT() - is
   what changes this line. A connection NOT built through that factory still sends
   whatever its own caller typed, so transport_parameters_wire_order above stays the
   measurement and this paragraph stays prose.

2. A KNOWINGLY VIOLATED MUST: A4-minimal never acknowledges a 1-RTT packet, including
   the one carrying HANDSHAKE_DONE, because it cannot send a 1-RTT packet at all.
   RFC 9000 s13.2.1, whole sentence past its line wrap (extract lines 59-61): "An
   endpoint MUST acknowledge all ack-eliciting Initial and Handshake packets
   immediately and all ack-eliciting 0-RTT and 1-RTT packets within its advertised
   max_ack_delay, with the following exception." One MUST, two conjuncts; 1-RTT is
   named and only its DEADLINE is relaxed. s13.2.1's exception covers an endpoint that
   "might not have packet protection keys for decrypting Handshake, 0-RTT, or 1-RTT
   packets when they are received" - we decrypted the packet, so it does not apply.
   A server will retransmit its HANDSHAKE_DONE unacknowledged. THIS IS A VIOLATION,
   not a soft deviation, and task 14 closes it.

3. AckDelayExponent IS WIRED AND VALIDATED BUT NOT OBSERVABLE. The connection loop
   reads the clock once per pump, so every ack_delay it reports is structurally zero
   and the exponent scales a zero - it moves no wire byte yet. RFC 9000 s13.2.5's
   reader subtracts the reported delay from its RTT sample, so under-reporting makes
   the peer's estimate more conservative, which is the safe direction and is taken
   deliberately. The connection fails loudly at construction if the scaled and
   advertised values disagree.

4. AckRangeLimit's DEFAULT OF 32 IS A PLACEHOLDER. The Brave capture says nothing
   about ACK ranges and no published vector does either, so it sits in the same
   not-yet-known-from-the-capture category as the initial packet number and the
   initial_rtt range. It is a real knob - it bounds bytes on the wire - but its value
   is not evidence about Chromium.

5. initial_source_connection_id FRESHNESS IS UNOBSERVABLE AT THE TARGET'S OWN SHAPE.
   Chromium's source connection ID is zero bytes, which erases the header field that
   would witness the parameter agreeing with it. The connections behind this readout
   advertise a five-byte one so the agreement is witnessable at all; the field above
   says so rather than claiming a witness the target's shape removes.
