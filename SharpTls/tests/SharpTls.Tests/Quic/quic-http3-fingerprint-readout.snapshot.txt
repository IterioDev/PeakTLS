## Notes on the third column

SETTINGS WIRE ORDER IS MEASURED AND STILL NOT-YET-KNOWN, and those are not in
tension. Finding 7: the capture's identifiers are "1, 6, 7, 51, 126585778853 -
strictly ascending. So Chromium's emission order and a sort by identifier are
indistinguishable from this capture alone." Reading OUR order off the wire, which
this readout does, says nothing about BRAVE's. A capture of Chromium emitting a
non-ascending set retires it.

THE ALPN ROW IS DECODED FROM THE CLIENTHELLO. It used to sit in the third column
with a pasted grep result for a value, because this readout was never handed the
ClientHello. It is now: Describe requires the encoded handshake message and the row
is read back out of it by the library's own importer, so the ours column is a
function of emitted bytes like every other row here. The whole offered list is
compared against the capture's single token, not searched for h3 inside it - RFC
9114 s3.2 lets a conforming client offer more, and one that does is a different
client.

THE ROWS MARKED [subsystem B] ARE NOT SCORED AGAINST C. Perk segments 3 and 4 live
in the ClientHello, under RFC 9001 s5.2's Initial keys, and TlsQuicFingerprintReadout
already reads them off the emitted datagrams - it is the instrument, not this file.
The transport-parameter wire order MISMATCH is task 11's finding re-rendered so a
perk readout is not silently missing a perk segment, not a fresh filing against C.

THE FIVE SETTINGS PAIRS AND THE PSEUDO-HEADER ORDER ARE NEVER not-yet-known. The
capture publishes both affirmatively - its SETTINGS table at lines 64-68 and its
pseudo-header line at 70 - so those rows carry match or MISMATCH and nothing else.
