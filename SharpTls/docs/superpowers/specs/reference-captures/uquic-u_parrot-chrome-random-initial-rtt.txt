WHAT IT SAYS - bounds, units, distribution
  bounds:       const minRTT, maxRTT = 1000, 20000
  units:        MICROSECONDS. Stated by the doc comment ("a random realistic RTT
                value in microseconds", "the range 1000-20000 us"). The code
                carries no time.Duration; the value goes straight onto the wire as
                a QUIC varint. So 1000 us = 1 ms and 20000 us = 20 ms.
  distribution: UNIFORM, over the half-open interval [1000, 20000). crypto/rand
                (imported as "rand"; math/rand is the separate "mrand") draws
                rand.Int over [0, maxRTT-minRTT) = [0, 19000) and adds minRTT, so
                20000 itself is never produced; the realised set is the 19000
                integers 1000..19999.
  redrawn:      per call to QUICID2Spec, i.e. per spec build, NOT per dial of a
                reused spec - see the QUICID2Spec doc comment quoted below.

*** THE OBSERVED 192859 IS OUTSIDE THIS RANGE. THIS FUNCTION DOES NOT SETTLE  ***
*** DeclaredInitialRttRange. DO NOT ADOPT 1000-20000 AS THE BRAVE 151 RANGE.  ***

  A client capture
  (the preset that measured it, line 91) records
  initial_rtt = 192859. That is 192859 us = 192.9 ms, roughly 9.6x this
  function's maximum and 193x its minimum. It cannot be a draw from
  [1000, 20000).

  Three independent readings of the code below say the same thing, and none of
  them can be reconciled away:

  1. Range. 192859 > 20000. Directly.
  2. Encoding. The function emits a TWO-byte QUIC varint - val is literally two
     bytes, prefix 0b01 - whose maximum representable value is 16383. 192859
     needs a four-byte varint (max 1073741823). Whatever that client put on the wire
     was not encoded the way this function encodes.
  3. The function's own numbers do not close. maxRTT is 20000 but the two-byte
     varint holds 16383, so every draw in [16384, 19999] silently loses its
     overflow bits: byte(0x40|byte(rtt>>8)) keeps only the low 6 bits of the high
     byte, so e.g. 16384 encodes as 0. The effective on-wire distribution is
     therefore NOT the documented one. (Readings 2 and 3 are read off the code
     below - they are not claims the code makes about itself.)

  The doc comment also records uQUIC's own single observation: "The observed
  value in the reference pcap was 7740 us". So there are now two single draws
  from the real world - 7740 us (uQUIC's Chrome 146 pcap) and 192859 us (this
  repo's client capture) - a factor of 25 apart, and BOTH inside the range of
  a plausible measured network RTT. The simplest reading consistent with both is
  that Chromium reports a path-derived RTT estimate rather than drawing a random
  number, in which case there is no fixed distribution to copy and 1000-20000 is
  uQUIC's invention for imitation purposes, fitted to one sample. That reading is
  an inference from two data points; it is NOT established here.

// ChromeRandomInitialRTT returns a FakeQUICTransportParameter for google_initial_rtt (0x3127).
// Chrome 146 includes this parameter with a random realistic RTT value in microseconds.
// The observed value in the reference pcap was 7740 µs; the range 1000–20000 µs covers
// typical network conditions. Value is encoded as a 2-byte QUIC varint (high bits = 0b01).
func ChromeRandomInitialRTT() *tls.FakeQUICTransportParameter {
	const minRTT, maxRTT = 1000, 20000
	r, err := rand.Int(rand.Reader, big.NewInt(maxRTT-minRTT))
	if err != nil {
		panic(err)
	}
	rtt := uint16(minRTT + r.Int64())
	// 2-byte QUIC varint: top 2 bits = 01, remaining 14 bits = value
	val := []byte{byte(0x40 | byte(rtt>>8)), byte(rtt)}
	return &tls.FakeQUICTransportParameter{Id: 0x3127, Val: val}
}
